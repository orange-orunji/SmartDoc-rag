## 一、项目整体介绍

### Q1：请简单介绍一下这个项目
**考察点**：项目概述能力、业务理解

**回答要点**：
- 这是一个**企业级 AI 办公助手**，面向知识管理与办公自动化场景
- 核心能力：知识库文档检索问答、AI 报告生成、文件格式转换（md/txt/docx）、邮件发送（SMTP + 附件）
- 技术栈：FastAPI + LangChain Agent + Chroma 向量库 + RabbitMQ + Redis + SQLite
- 特色：**三阶混合检索（HyDE + 向量 + BM25 + Rerank）**、Agent 自主决策（6 个 Function Calling 工具）、双层缓存（MD5 + 语义相似度）、异步文档处理、SSE 流式对话、多用户 JWT 认证 + 会话隔离

### Q2：这个项目的最大技术亮点是什么？
**考察点**：对项目的深度理解

**回答要点**：
- **HyDE（假设文档嵌入）检索增强**：用 LLM 先生成"假想答案"再检索，桥接用户口语化提问与文档正式用语之间的语义鸿沟，实验数据 Recall@1 从 53% 提升到 67%
- **Function Calling Agent**：6 个工具（search/upload/status/report/convert/email）自主决策调用，从检索到报告生成到邮件发送形成完整闭环
- **双层缓存**：MD5 精确匹配（Redis）+ 语义相似度匹配（内存向量 + DashScope Embedding），缓存命中延迟从 ~20s 降至 ~0.01s
- **量化评估体系**：内置 Recall@K、MRR 自动化评测脚本，支持 4 种检索策略 A/B 对比
- **异步架构**：RabbitMQ Topic 交换机 + Redis 文件暂存 + 内嵌 Worker + 任务状态追踪（Pending→Processing→Completed/Failed）

### Q3：项目中有哪些你觉得可以改进的地方？
**考察点**：批判性思维、架构演进意识

**回答要点**：
- Agent 当前基于 `langchain_classic` 的 `AgentExecutor`（官方已标记为 legacy），计划迁移到 **LangGraph**：
  - 用 StateGraph 实现"必须先检索再回答"的硬约束，而非 Prompt 软约束
  - 用 Checkpointer 接管多轮记忆，告别手工拼接历史文本
  - 敏感操作（如发邮件）增加人机协同中断确认
- BM25 在小规模文档集上效果不佳（IDF 统计不可靠），后续按查询意图分类按需启用
- 当前 `KnowledgeBaseService` 和 `VectorStoreService` 各自创建 Chroma 实例，存在连接冗余

## 二、RAG 检索增强生成

### Q4：RAG 的整体流程是怎样的？
**考察点**：RAG 基础原理

**回答要点**：
1. **离线阶段**：文档上传 → 解析（`_extract_text` 按 .pdf/.docx/.md/.txt 后缀分发 PyPDF2/python-docx）→ `RecursiveCharacterTextSplitter` 分割（chunk_size=500, overlap=50）→ DashScope Embedding 向量化 → 存入 Chroma；同时计算 MD5 记录到 `md5_records.txt`
2. **在线阶段**：用户提问 → HyDE 假设文档生成（一次 LLM 调用）→ 向量检索（DashScope）+ BM25 关键词检索（jieba 分词）→ 按 `page_content` 去重合并 → BGE-Reranker Cross-Encoder 重排序 → Top-K 上下文 → LLM 生成回答 → SSE 流式返回

### Q5：为什么要用 HyDE？它的原理是什么？
**考察点**：检索增强技术深度

**回答要点**：
- **核心问题**：用户提问往往是口语化的（"怎么用 Git"），而文档内容是正式书面语（"Git 版本控制操作指南"），直接向量检索存在语义鸿沟
- **HyDE 解法**：让 LLM 根据用户问题**先生成一段"假设文档"（Hypothetical Document）**，再用这段假设文档去向量库中检索。假设文档的用词语境更接近真实文档
- **实现**（`app/services/hyde.py`）：`generate_hypothetical(question)` → `_vs.get_vector(query=假想文本, k=k)`，本质是用 LLM 输出替代原始 query 做 Embedding
- **效果**：实验数据表明，仅加入 HyDE 就将 Recall@1 从 53.33% 提升到 60.00%，HyDE+Rerank 达到 66.67%
- **代价**：多一次 LLM 调用，增加约 1~2s 延迟

### Q6：混合检索是怎么做的？为什么需要混合检索？
**考察点**：检索策略设计

**回答要点**：
- **向量检索**（语义匹配）：适合模糊语义问题，如"怎么提升代码质量"
- **BM25 关键词检索**（`rank_bm25.BM25Okapi` + `jieba` 分词）：适合精确专有名词查询，如"Redis 持久化 RDB AOF"
- **Rerank 重排序**（`CrossEncoder("bge-reranker-base")`）：对合并候选集联合编码打分
- **合并策略**：向量检索取 top-15，BM25 取 top-10，按 `page_content` 字典键去重后送入 Reranker 取 top-3
- **实验结论**：小规模文档集下 BM25 可能引入噪声，HyDE+Rerank 是当前综合最优策略

### Q7：Chroma 和 DashScope Embedding 是怎么用的？
**考察点**：向量数据库实操

**回答要点**：
- Chroma 本地持久化：`persist_directory="app/data/storage/chroma_db"`，`collection_name="enterprise_knowledge"`
- 嵌入模型：`DashScopeEmbeddings(dashscope_api_key=...)`（阿里云，1024 维）
- 两个服务类各自创建了 Chroma 实例——`VectorStoreService` 负责检索，`KnowledgeBaseService` 负责入库
- 元数据结构：`{"source": filename, "create_time": ..., "operator": user_id, "md5": ..., "chunk_index": i, "total_chunks": n}`
- `get_all_documents()` 从 `chroma.get()` 获取全部数据，重组为 `list[Document]`
- 启动时通过 `lifespan` 自动调用 `BM25Service().build_index(all_docs)` 重建索引

### Q8：文本分割的 chunk_size 和 overlap 是如何选择的？
**考察点**：文档处理经验

**回答要点**：
- `RecursiveCharacterTextSplitter`：`chunk_size=500`，`chunk_overlap=50`（10%）
- 分隔符优先级：`["\n\n", "\n", "\t", " ", ".", ",", "!", "?", ";", "。", "，"]`
- 500 平衡语义完整性和检索精度（太小断裂上下文，太大噪声多）
- 中英文混合分隔符支持多语种文档
- 长度判断：若文本 ≤ chunk_size 则不分块，整段入库

### Q9：BGE-Reranker 是怎么工作的？为什么需要它？
**考察点**：重排序模型原理

**回答要点**：
- `BGE-Reranker-Base`（本地 `sentence-transformers/CrossEncoder`），模型文件存于 `models/bge-reranker-base/`
- **Bi-Encoder vs Cross-Encoder**：向量检索是 Bi-Encoder（query 和 doc 独立编码），速度快精度有限；Reranker 是 Cross-Encoder（`[[query, doc_content], ...]` 联合编码打分），精度高速度慢
- **策略**：Bi-Encoder 粗召回（高召回率）→ Cross-Encoder 精排（高精度），兼顾效率与效果
- 选用 Base 而非 Large/M3：**本地推理速度与资源平衡**

### Q10：在什么情况下 BM25 检索反而降低了召回率？
**考察点**：检索策略批判性分析

**回答要点**：
- 实验显示：纯模糊语义场景下，HyDE+Rerank 的 Recall@1=66.67%，加入 BM25 后降至 50.00%
- **原因**：
  1. 小文档集（13 篇）下 IDF 统计不可靠，无法区分专有词与普通词
  2. 模糊问题缺乏精确关键词，BM25 匹配的多是噪声
  3. 去重合并时噪声文档挤占相关文档排名
- **BM25 适用前提**：① 文档规模足够大；② 查询包含明确专有词汇

## 三、LangChain Agent 与 Function Calling

### Q11：Agent 是怎么设计的？有哪些工具？
**考察点**：Agent 架构设计

**回答要点**：
- 基于 `langchain_classic` 的 `create_tool_calling_agent` + `AgentExecutor` 封装
- LLM 使用 `ChatOpenAI` 连接 DeepSeek API（硅基流动代理），`streaming=True`
- `@lru_cache(maxsize=None)` 实现 Agent 单例
- **6 个 Function Calling 工具**（均用 `@tool` 装饰器）：
  1. `search_knowledge_base(query)` — 三阶混合检索全流程
  2. `upload_document(rep_input)` — 文本内容入库，兼容 JSON/纯文本传参
  3. `get_document_status(keyword)` — 知识库统计 + 关键词过滤
  4. `generate_report(topic, format)` — 检索→LLM 汇总→Markdown→SSE 推送下载
  5. `convert_format(filename, target_format)` — md↔txt↔docx 互转 + Markdown 清洗
  6. `send_email(to, subject, body, attachment)` — SMTP + TLS + MIMEBase 附件
- Prompt 核心原则："所有提问默认先调用 search_knowledge_base 检索知识库"

### Q12：Agent 的 Prompt 是怎么设计的？
**考察点**：Prompt Engineering

**回答要点**：
- `ChatPromptTemplate.from_messages` 三层结构：
  1. **系统角色**："企业知识库助手，帮助用户从已上传文档中查找信息"
  2. **核心原则**："所有提问默认先调 search_knowledge_base 检索，不得未经检索凭训练知识回答"
  3. **例外规则**：纯社交用语（谢谢/好的）、数学计算、用户明确说不用查文档
- 每个工具 docstring 注明**适用/不适用场景**，LLM 据此做路由决策
- 回答格式约定："根据知识库文档："vs"根据通用知识："，冲突时知识库优先
- `MessagesPlaceholder(variable_name="agent_scratchpad")` 记录 Agent 思考过程

### Q13：AgentExecutor 的流式输出是怎么处理的？
**考察点**：Agent 流式输出机制

**回答要点**：
- `chain.astream({"input": history_text + question})` 异步流式调用（注意：参数 key 是 `input`）
- 解析三种 chunk 类型（**key 用复数** `actions`/`steps`，不是单数）：
  - `"actions"` → 推送 `[调用工具: xxx | 输入: ...]` 到前端
  - `"steps"` → 检测 `[REPORT_FILE]` 标记，自动推送下载按钮 HTML `<a href='/reports/{filename}' download>`
  - `"output"` → 最终文本，逐 token 拼接
- SSE 协议：`data: {content}\n\n`，换行符转义 `\n`→`\\n`，`[DONE]` 结束
- 流式结束后：`history.add_message(HumanMessage)` + `history.add_message(AIMessage)` 双次写入持久化，同时存入双层缓存

### Q14：LangChain 工具定义时有哪些坑？
**考察点**：LangChain 实战经验

**回答要点**：
- **`@tool` 使函数变为 `StructuredTool` 对象**，不能直接调用。需通过 Agent 或 `.invoke()` 间接调用，结果处理取 `.content` 属性
- **多参数工具必须加 `args_schema`**（Pydantic 模型），否则 LLM 脑补参数格式导致解析失败
- **docstring 优先级高于函数名**：工具描述以 docstring 为准，函数名仅作标识
- **LLM 参数脑补陷阱**：LLM 可能将纯文本对话当 JSON 传入工具。解决：`json.loads(rep_input, strict=False)` 失败后按 `\n` 切分为 `filename` 和 `content`
- **参数命名**：用 `filename`/`content` 而非 `file_name`/`file_type`，LLM 对无下划线命名理解更稳定

### Q15：为什么计划从 AgentExecutor 迁移到 LangGraph？
**考察点**：技术选型与架构演进

**回答要点**：
- `AgentExecutor` 三个核心局限：
  1. 流程只能靠 Prompt 软约束，模型可能跳过检索
  2. 对话历史需手工拼接（`history_text + body.question`）
  3. 非真正 token 级流式（分阶段返回 chunk）
- **LangGraph 优势**：StateGraph 硬约束流程 + Checkpointer 自动管理多轮状态 + 真 token 级流式 + `interrupt` 人机协同

## 四、文件解析与文档处理

### Q16：文件解析是怎么实现的？支持哪些格式？
**考察点**：文档处理能力

**回答要点**：
- 统一入口 `_extract_text(content: bytes, suffix: str) -> str`，按后缀分发：
  - `.txt` / `.md`：`content.decode("utf-8", errors="ignore")`
  - `.pdf`：`PyPDF2.PdfReader(BytesIO(content))` → 逐页 `page.extract_text()`
  - `.docx`：`python-docx.Document(BytesIO(content))` → 逐段 `para.text`
- 每种格式有 `ImportError` 保护，缺失依赖时抛明确异常
- `BytesIO` 内存流处理，无需落盘
- 上传前校验：文件大小 ≤10MB（`MAX_FILE_SIZE`），后缀白名单 `.txt/.docx/.pdf/.md`
- 空内容检测：`if not text.strip()` → 拒绝入库

### Q17：MD5 去重是怎么实现的？为什么要做？
**考察点**：去重策略设计

**回答要点**：
- **实现**（`KnowledgeBaseService.upload_by_str`）：
  1. `get_string_md5(data)` 计算文本内容 MD5
  2. `check_md5(md5_file_path, md5_value)` 逐行比对 `md5_records.txt` 中的历史记录
  3. 已存在 → 返回 `"[Pass] 文件已存在,请勿重复上传"`，跳过入库
  4. 不存在 → `RecursiveCharacterTextSplitter` 分块 → `chroma.add_texts` 向量化 → `save_md5` 追加
- **为什么**：按**内容**去重而非文件名（即使改名也能识别），节省向量存储和检索计算
- **局限**：仅精确匹配，无法检测"内容稍作修改"的文档；记录基于文本追加，无索引结构

### Q18：文档入库时的元数据包含哪些信息？为什么重要？
**考察点**：向量数据库元数据设计

**回答要点**：
- 每个 chunk 的 metadata：
  ```python
  {"source": filename, "create_time": "2026-07-21 12:00:00",
   "operator": user_id, "md5": md5_hash,
   "chunk_index": i, "total_chunks": len(chunked_array)}
  ```
- `source`：检索结果可追溯来源文件，`get_document_status` 按文件名分组统计
- `create_time`：判断信息时效性
- `operator`：多用户追溯上传者
- `md5`：关联原始文件
- `chunk_index / total_chunks`：知道片段在原文中的位置，支持上下文衔接

## 五、消息队列与异步处理

### Q19：为什么需要 RabbitMQ？文档上传的异步流程是怎样的？
**考察点**：消息队列设计

**回答要点**：
- **同步问题**：PDF 解析 + 分块 + 向量化 + Chroma 写入 + BM25 重建，耗时 10~30s
- **异步方案**：
  1. API 校验 → 文件内容 hex 写入 Redis（`file:content:{task_id}`，600s 过期）
  2. 发布消息到 Topic 交换机 `document.tasks`，routing_key=`document.upload` → HTTP 202 + task_id
  3. 内嵌 Worker（`lifespan` 中 `asyncio.create_task`）消费 → hex 还原 → 解析 → 入库 → 重建 BM25
  4. 用户 `GET /api/document/upload/status/{task_id}` 轮询状态（`TaskTracker` 基于 Redis）
- **可靠性**：消息持久化 `PERSISTENT`、死信队列 DLX、幂等检查 `task:processed:{task_id}`、重试 3 次间隔 5s

### Q20：RabbitMQ 消息的可靠性和幂等性是怎么保证的？
**考察点**：消息队列高级特性

**回答要点**：
- **可靠性四层**：消息持久化 + 死信队列（`x-dead-letter-exchange`）+ 手动 Ack（`async with msg.process()`）+ 消费重试（最多 3 次，间隔 5s）
- **幂等性**：Redis key `task:processed:{task_id}`（24h 过期），消费前 `redis.exists()` 检查
- 配合 RabbitMQ `at-least-once` 语义，防止重复消费

### Q21：RabbitMQ 连接失败时系统怎么处理？
**考察点**：容错设计

**回答要点**：
- `lifespan` 中连接 `try/except` 包裹，失败时 `logger.warning`，`mq_connected=False`，不阻塞启动
- 降级：异步上传功能禁用；检索问答、报告生成、邮件等完全正常
- 连接成功后自动启动内嵌 Worker

### Q22：任务状态追踪是怎么实现的？
**考察点**：异步任务状态管理

**回答要点**：
- `TaskTracker` 基于 Redis，key 格式 `task:document:{task_id}`，1h 过期
- 状态枚举：`Pending → Processing → Completed / Failed`
- `set_status(task_id, status, extra)` 存 JSON，`get_status(task_id)` 读取
- 前端 `pollStatus(taskId)` 每 2s 轮询，完成/失败后停止

## 六、缓存策略

### Q23：双层缓存是怎么设计的？
**考察点**：缓存架构

**回答要点**：
- **第一层：语义相似度缓存**（`SemanticCache`，内存向量）
  - 历史问题 DashScope Embedding 向量存内存列表
  - 新问题编码 → 余弦相似度（`np.dot`，向量已 L2 归一化）→ 阈值 0.85
  - 优点：能匹配"换一种问法"的相似问题
- **第二层：MD5 精确匹配缓存**（Redis）
  - `hashlib.md5(question).hexdigest()` → key=`qa:{user_id}:{hash}`
  - 完全相同提问命中后直接返回，600s 过期
- **查询顺序**：语义缓存 → MD5 缓存 → 正常 LLM 调用
- **写入时机**：流式对话结束后同时写两层缓存 + 对话历史
- **效果**：缓存命中延迟 ~20s → ~0.01s

### Q24：语义缓存的向量相似度是怎么计算的？
**考察点**：向量计算原理

**回答要点**：
- `DashScopeEmbeddings.embed_query(text)` → 1024 维向量 → L2 归一化 `arr / np.linalg.norm(arr)`
- 余弦相似度退化为点积：`np.dot(matrix, query_vec)`
- `np.argmax(scores)` 取最相似项，阈值 0.85（平衡命中率和准确性）
- 缓存 key：`qa:semantic:{user_id}:{md5_hash[:12]}`，按用户隔离

### Q25：Redis 不可用时影响哪些功能？降级策略是怎样的？
**考察点**：降级策略

**回答要点**：
- Redis 采用**懒加载 + 连接失败返回 None**（`get_redis()` 初次连接失败设 `_redis_client=None`）
- 所有调用方 `if redis:` / `if not redis: return None` 判断
- **受影响**：双层缓存、异步上传、任务状态追踪、幂等性检查
- **不受影响**：知识库检索问答、报告生成、对话历史（JSON 文件）、JWT 认证（SQLite）

## 七、认证与安全

### Q26：JWT 认证是怎么实现的？
**考察点**：认证机制

**回答要点**：
- `python-jose` 实现 JWT（HS256），`SECRET_ID` 密钥
- 密码：`passlib` 的 `pbkdf2_sha256` 哈希，注册时检查密码 ≤ 72 字节（bcrypt 限制）
- Token 有效期 7 天（`60*24*7` 分钟）
- `HTTPBearer` + `Depends(get_current_user)` 依赖注入验证，解析出 `{"user_id": 1, "sub": "username"}`
- 前端存 `localStorage`，请求带 `Authorization: Bearer {token}`
- 多用户数据物理隔离：`chat_history/{user_id}/{session_id}.json`

### Q27：接口限流是怎么做的？
**考察点**：安全防护

**回答要点**：
- `slowapi` + `SlowAPIASGIMiddleware`，基于客户端 IP 的 `Limiter`
- 聊天接口 `@limiter.limit("10/minute")`
- 可配置开关 `RATE_LIMIT_ENABLED`，超限返回 429
- 注意：限流装饰器函数签名**必须含 `request: Request` 参数**，否则 slowapi 无法正确读取

## 八、前端全栈实现

### Q28：前端是怎么实现的？用了什么技术？
**考察点**：全栈能力

**回答要点**：
- **纯 HTML/CSS/JS 单页应用**，零前端框架依赖，FastAPI `StaticFiles` 直接托管
- 登录/注册（Tab 切换）→ 聊天主界面（左侧边栏 + 右侧对话区）双页面架构
- 核心 JS 功能：
  - **SSE 流式接收**：`fetch + ReadableStream` 读取（不用 `EventSource`，因为需要 POST + 自定义 headers）
  - **Markdown 渲染**：`marked.js`（CDN 引入 `cdn.jsdelivr.net/npm/marked`），`marked.parse(text)`
  - **会话管理**：新建/切换/重命名/删除，UUID 短 ID，`localStorage` 存 token
  - **文档上传**：`FormData` + 文件选择器，上传后轮询
- 响应式 `@media (max-width: 768px)`，CSS 变量主题，打字机动画

### Q29：SSE 流式对话在前端是怎么处理的？
**考察点**：SSE 客户端实现

**回答要点**：
- 不用 `EventSource`（不支持 POST + 自定义 headers），用 **`fetch + ReadableStream`**：
  ```javascript
  const resp = await fetch('/api/chat/stream', {
      method: 'POST',
      headers: { ...authHeaders(), 'Content-Type': 'application/json' },
      body: JSON.stringify({ question, session_id: currentSessionId })
  });
  const reader = resp.body.getReader();
  const decoder = new TextDecoder();
  ```
- 分块读取 + buffer 拼接：`buffer += decoder.decode(value, {stream: true})`
- 按 `\n` 分割行，过滤 `data:` 前缀，跳过 `[DONE]`
- 逐块更新 DOM：`bubble.innerHTML = formatContent(fullResponse)`，配合 `scrollToBottom()`
- 还原 SSE 转义：`text.replace(/\\n/g, '\n')` 后再交给 marked 渲染

### Q30：`marked.js` 渲染 Markdown 有什么注意点？
**考察点**：前端渲染细节

**回答要点**：
- `marked.parse()` 对标准 Markdown（表格/代码块/标题/列表）支持良好
- **容易踩的坑**：特殊格式（自定义前缀标记、内嵌 JSON）可能被 marked 当作无效标记**无声吞掉**
- **解决**：需要保留的特殊内容直接推 HTML 标签（如 `<a href='/reports/xxx' download>`），marked 会原样渲染
- 下载按钮就是通过后端直接推 HTML `<a class="download-link">` 实现的，绕过 marked 处理

## 九、数据存储设计

### Q31：项目的数据库是怎么设计的？
**考察点**：数据库选型与设计

**回答要点**：
- **SQLite + SQLAlchemy ORM**，数据库文件 `app.db`
- 用户表 `users`：`id(Integer PK) + username(String unique) + hashed_password(String)`
- 连接池配置：`pool_size=5, max_overflow=10, pool_timeout=30, pool_recycle=3600, pool_pre_ping=True`
- **WAL 模式**：`@event.listens_for(engine, "connect")` 设置 `PRAGMA journal_mode=WAL` + `PRAGMA foreign_keys=ON`，支持并发读写
- 开发环境 `echo=True` 打印 SQL
- `Base.metadata.create_all(bind=engine)` 在 lifespan 启动时自动建表

### Q32：对话历史是怎么持久化的？
**考察点**：文件存储设计

**回答要点**：
- 自研 `FileChatHistory(BaseChatMessageHistory)`，存储结构 `chat_history/{user_id}/{session_id}.json`
- 序列化：`message_to_dict()` → `json.dump()`（全量覆盖，非追加）
- 反序列化：`json.load()` → `messages_from_dict()` → `list[BaseMessage]`
- `add_message` 实现：读取当前列表 → 追加新消息 → 全量序列化写回
- 边界处理：文件不存在返回 `[]`；JSON 解析失败捕获异常返回 `[]`；路径为文件时自动删文件建目录
- 初始化时 `os.makedirs(storage_path, exist_ok=True)` 确保目录存在

### Q33：`current_user_ctx` 上下文变量是干什么的？
**考察点**：Python 跨层传参

**回答要点**：
- `contextvars.ContextVar[str]` 实现**请求级别 user_id 透传**，默认值 `"agent"`
- **背景**：Agent Tool 函数定义在模块级别，无法通过函数参数接收 FastAPI 的 `Depends(get_current_user)` 注入的 user_id
- **方案**：API 层 `current_user_ctx.set(user_id)`，Tool 内部 `current_user_ctx.get()`
- `contextvars` 协程安全：每个异步任务有独立上下文副本

### Q35：FastAPI 的 lifespan 中做了哪些初始化？
**考察点**：应用生命周期管理

**回答要点**：
- `@asynccontextmanager` 异步 lifespan
- **启动时**：RabbitMQ 连接（try/except 不阻塞）→ 内嵌 Worker 启动（`asyncio.create_task`）→ BM25 全量索引构建（`chroma.get()` → `BM25Service().build_index()`）→ SQLite 表创建
- **关闭时**：`worker_task.cancel()` → 处理 `CancelledError` → `rabbitmq.close()`
- 日志在模块加载时初始化：`logging.basicConfig(level=..., format=..., datefmt=...)`

### Q36：SSE 流式对话的后端实现细节？
**考察点**：服务端推送实现

**回答要点**：
- `StreamingResponse(event_stream(), media_type="text/event-stream")`
- `event_stream` 是 async generator：`yield f"data: {_sse_escape(content)}\n\n"`
- `_sse_escape(text)`：`text.replace('\n', '\\n')`，防止破坏 SSE `data:` 行格式
- 缓存检查在进入 generator 之前完成（语义 → MD5 → 正常流程）
- 对话历史在 `finally` 块中持久化（保证异常时也写入）
- 性能注意：`astream` chunk 可能是 `AIMessageChunk`，需判空 `if text is None or len(text) == 0: continue`

### Q37：项目是怎么做检索效果评估的？
**考察点**：质量保障

**回答要点**：
- 手工测试集 `eval_questions.json`（30 模糊 + 13 精确），each: `question` + `expected_keywords`
- 评估指标：**Recall@K**（Top-K 含预期关键词 → 命中率）+ **MRR**（第一个正确答案排名倒数均值）
- `eval_retrieval.py` 自动化，4 种策略对比：Baseline / HyDEOnly / HyDE+Rerank / HyDE+BM25+Rerank
- 实验结论写入 `EVALUATION.md`：HyDE+Rerank 模糊场景 Recall@1=66.67%

### Q38：Docker 部署是怎么设计的？
**考察点**：容器化部署

## 十一、系统设计对比

### Q39：为什么选 Chroma 而不是 Milvus / Qdrant / FAISS？
**考察点**：技术选型判断力

**回答要点**：
- **Chroma 适合当前场景**：轻量级、零配置、嵌入式运行、Python 原生支持、与 LangChain 深度集成
- **不需要 Milvus/Qdrant 的原因**：当前数据量小（13 篇文档），不需要分布式/高并发。Chroma 的 `persist_directory` 本地持久化已满足需求
- **FAISS 的取舍**：FAISS 纯内存索引，性能极高但无持久化（需额外序列化）。语义缓存中用了 Faiss-like 的内存向量计算，但主存储选 Chroma 是看中其持久化能力
- docker-compose 中已预留了 Chroma 独立服务模式的升级路径

### Q40：为什么用 FastAPI 而不是 Flask / Django？
**考察点**：框架选型

**回答要点**：
- **异步原生支持**：`async/await` 一等公民，Agent 流式调用 + SSE 推送 + RabbitMQ 异步消费天然契合
- **类型安全**：Pydantic 模型自动生成 OpenAPI 文档 + 请求校验
- **依赖注入**：`Depends` 优雅管理认证、数据库会话
- **性能**：基于 Starlette，异步性能优于 Flask
- **不用 Django**：不需要 ORM 全栈能力（只有一张用户表），Django 的"电池全含"反而过重
- **不用 Flask**：Flask 异步支持是后来加的，不如 FastAPI 原生；没有自动文档生成

### Q41：LLM 选型上为什么用 DeepSeek 而不是直接调 OpenAI？
**考察点**：API 选型

**回答要点**：
- 通过硅基流动（SiliconFlow）代理调用 DeepSeek，兼容 OpenAI 协议（`ChatOpenAI` 直接使用）
- **成本优势**：DeepSeek 性价比远高于 GPT-4
- **中文能力**：DeepSeek 中文理解与生成质量优秀，适合中文企业知识库场景
- **兼容性**：OpenAI 兼容协议使 LangChain 集成零成本（只需改 `base_url` 和 `api_key`）
- DashScope Embedding 同理：中文 Embedding 效果优于 OpenAI `text-embedding-ada-002`

### Q42：`@lru_cache` 在项目中是怎么用的？
**考察点**：Python 装饰器

**回答要点**：
- `get_agent()` 和 `get_settings()` 使用 `@lru_cache(maxsize=None)` 实现单例

- `Depends(get_db)`：管理数据库会话生命周期（`yield db` → `finally db.close()`）
- 认证失败自动抛 `HTTPException(401)`

### Q44：`Pydantic` 和 `pydantic-settings` 的区别？

## 十三、开放性问题

### Q45：如果你要重新设计这个项目的检索链路，你会怎么做？
**考察点**：系统设计能力

**参考思路**：
- 引入**查询意图分类**：先判断模糊语义 / 精确关键词，按需启用 BM25
- **多路召回融合**（RRF 算法）替代简单的拼接去重
- **RAPTOR / 层次化索引**处理长文档跨段落检索
- **Self-RAG / Corrective RAG**：检索后自评相关性，不足时自动补充检索

### Q46：项目中遇到的最棘手的技术问题是什么？怎么解决的？
**考察点**：问题解决能力

**参考思路**：
- **Agent 工具参数 LLM 脑补**：LLM 将对话文本当 JSON 传参 → 工具内 `json.loads(strict=False)` + 纯文本 fallback + `args_schema` 约束
- **`@tool` 使函数变为不可调用对象**：测试困难 → 理解 LangChain Tool 机制，内部逻辑直调底层函数（如 `hyde_plus_rerank_bm25_retrieve`）
- **小模型 ReAct 格式输出不稳定** → 切换到 Function Calling 模式 + 明确 Prompt 约束
- **RabbitMQ Docker 重启后队列丢失** → 配置 `durable=True` + volume 挂载 `rabbitmq_data:/var/lib/rabbitmq`
- **marked.js 吞掉报告下载通知** → 后端直接推 HTML 标签而非 Markdown，绕过 marked 解析
