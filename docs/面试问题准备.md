## 一、项目整体介绍

### Q1：请简单介绍一下这个项目

**考察点**：项目概述能力、业务理解

**回答要点**：
- **DevSage · 研发智库**：面向**研发团队**的技术知识库 Agent——团队的技术规范、方案、复盘散落各处，新人上手慢、重复踩坑，用自然语言驱动从"查资料"到"交付文件"的完整闭环
- 核心能力：知识库检索问答（来源引用）、文档异步入库（RabbitMQ）、知识库统计、报告生成（一键下载）、格式转换（md/txt/docx）、邮件发送（人工审批）、文档删除
- 技术栈：Python 3.14 + FastAPI + LangGraph + Vue 3 + Vite + Chroma + RabbitMQ + Redis + SQLite
- 一句话特色：**LangGraph 自定义 StateGraph（检索前置硬约束）+ 三阶混合检索（HyDE/BM25/RRF/Rerank + 查询意图路由）+ 双层缓存（含一致性治理）+ HITL 人工审批 + 端到端评测体系 + Docker 一键部署**

### Q2：这个项目的最大技术亮点是什么？

**考察点**：对项目的深度理解、技术判断力

**回答要点**（挑 4–5 个讲，每个都带数据）：
1. **检索前置硬约束（自定义 StateGraph）**："先检索再回答"从 Prompt 软约束升级为**图的必经节点**；入口路由让社交/动作类请求跳过检索；知识类问题检索覆盖率 100%，动作类请求耗时 10.8s → 1.5s
2. **敏感操作人工审批（HITL）**：`send_email` 执行前 interrupt 挂起 → SSE 中断帧 → 前端审批卡片 → resume 恢复；审批状态存于 checkpointer，切会话/刷新/重启均可恢复
3. **三阶混合检索 + 意图路由**：HyDE 语义扩展 → 向量 + BM25 双路（RRF 融合）→ BGE-Reranker 精排（质量阈值 0.1 过滤）；300 题评测自适应策略 Recall@1 59.67%，反超全量混合基线 2pp；检索不足自动切换联网兜底
4. **双层缓存 + 一致性治理**：MD5 精确（Redis）+ 语义相似度（内存向量）；修复"工具调用轮写缓存导致假成功"缺陷（读侧拦截 + 写侧不写）；缓存命中延迟约 20s → 约 0.01s
5. **Agent 端到端评测体系**：38 题五分类评测（含压力题），全自动断言、零 LLM judge、断点续跑；配套一键重测脚本，基线全绿

## 二、RAG 检索增强生成

### Q5：RAG 的整体流程是怎样的？

**考察点**：RAG 基础原理

**回答要点**：
1. **离线阶段**：文档上传 → `_extract_text` 按 .pdf/.docx/.md/.txt 分发解析 → `RecursiveCharacterTextSplitter` 分割（500/50）→ DashScope Embedding → 存入 Chroma；内容 MD5 记入 `md5_records.txt` 去重
2. **在线阶段**：双层缓存检查 → **查询意图路由** → 检索（semantic：HyDE + 向量 + Rerank；keyword：HyDE + 向量 + BM25 双路 RRF + Rerank）→ Rerank 质量阈值（0.1）过滤 → 不足则**联网兜底** → LLM 生成 → SSE 流式返回 → 写缓存与历史

### Q6：为什么要用 HyDE？它的原理是什么？

**考察点**：检索增强技术深度

**回答要点**：
- **核心问题**：用户提问口语化（"怎么用 Git"），文档是正式书面语（"Git 版本控制操作指南"），直接向量检索存在语义鸿沟
- **解法**：让 LLM 先根据问题生成一段"假设文档"（假想答案），再用它去向量库检索——用假设文档的用词语境逼近真实文档
- **实现**（`app/services/hyde.py`）：`generate_hypothetical(question)` → `_vs.get_vector(query=假想文本, k=k)`
- **效果**：30 题模糊场景实验，Recall@1 从 53.33% 提升到 66.67%（HyDE + Rerank）
- **代价**：多一次 LLM 调用，增加约 1~2s 延迟

### Q7：混合检索是怎么做的？RRF 融合是什么？

**考察点**：检索策略设计

**回答要点**：
- **双路召回**：向量检索（语义匹配，取 top-15）+ BM25 关键词检索（`rank_bm25.BM25Okapi` + jieba 分词，取 top-10）
- **RRF 融合**（替代早期的暴力拼接去重）：分数 = Σ 1/(60 + rank)，只看排名不看原始分（免归一化）；**双路都召回的文档分数累加**，共识文档排名自然提升
- **精排**：融合后的候选集送 BGE-Reranker（Cross-Encoder 联合编码打分）取 top-3
- **策略路由**：不是每次都走双路——由查询意图路由器决定（见 Q8）

### Q8：BM25 什么时候反而拉低召回？意图路由器怎么解决？

**考察点**：检索策略批判性分析

**回答要点**：
- **问题**：小语料下 IDF 统计不可靠；模糊语义问题没有精确关键词，BM25 召回的是噪声（30 题实验：模糊场景混合后 66.67% → 50%）
- **解法：查询意图路由器三层漏斗**（`query_router.py`）：
  1. **第一层正则**：《》/引号/英文术语/版本号等精确标记 → 直接 keyword 通道；中文精确句式（是什么/有多少/怎么实现…）同样命中
  2. **第二层 IDF**：jieba 分词后查语料 IDF，最大 IDF > 4.0（稀有词信号）→ keyword
  3. **第三层默认**：→ semantic（HyDE 单路）
- **效果**：300 题评测路由判定正确率语义组 75.3% / 精确组 86.0%；检索层 Recall@1 59.67% 反超全量混合基线 2pp
- **提醒**：路由正确率只是代理指标，最终收益以 Recall@K 对比为准

### Q9：BGE-Reranker 是怎么工作的？质量阈值 0.1 怎么定的？

**考察点**：重排序模型原理 + 数据校准意识

**回答要点**：
- **Bi-Encoder vs Cross-Encoder**：向量检索是 Bi-Encoder（query/doc 独立编码，快但粗）；Reranker 是 Cross-Encoder（`[query, doc]` 联合编码打分，慢但准）→ 粗召回 + 精排两级
- **选型**：bge-reranker-base 本地推理（`models/bge-reranker-base/`），速度与效果平衡
- **分数落 metadata**：每个文档的 `rerank_score` 写入 metadata，供下游过滤
- **阈值 0.1**：实测相关文档 ≥0.42、不相关 0.00 → 阈值取 0.1 留安全边界；低于阈值视为"无有效结果"，触发联网兜底

### Q10：联网兜底机制是怎么设计的？

**考察点**：容错降级设计

**回答要点**：
- **触发条件**：前置检索经阈值过滤后上下文为空（`retrieval_context == ""`）→ 条件边自动切 `web` 节点
- **实现**：博查 API——`search_web()` 纯函数（带 URL / 发布日期格式化）+ `@tool` 双层复用；结果注入 `web_context`
- **答案分级标注**：知识库【来源：文件名】/ 网页【网页：标题】+URL / 通用知识三级体系，Prompt 强制标注来源
- **防跨轮残留**：`reset` 入口节点每轮清空 `retrieval_context` / `web_context`
- **失败降级**：未配置 Key 或调用失败 → 日志留痕、跳过联网，不影响知识库问答

### Q11：Chroma 和 Embedding 是怎么用的？

**考察点**：向量数据库实操

**回答要点**：
- Chroma 本地持久化（`persist_directory`），`collection_name` 独立；启动时从 Chroma 全量拉取重建 BM25 索引
- Embedding：DashScope 中文向量（统一工厂 `embedding_factory` 封装，支持按量计费模型切换）
- 元数据：`source` / `create_time` / `operator` / `md5` / `chunk_index` / `total_chunks` / `rerank_score`
- 规模上去了可平滑切独立服务（架构上已解耦）

### Q12：文本分割的 chunk_size 和 overlap 如何选择？

**考察点**：文档处理经验

**回答要点**：
- `RecursiveCharacterTextSplitter`：chunk_size=500、overlap=50（10%）
- 分隔符优先级 `["\n\n", "\n", "\t", " ", ".", ",", "!", "?", ";", "。", "，"]`，中英文混合支持
- 500 平衡语义完整与检索精度；overlap 50 防止跨块语义断裂
- 文本 ≤ chunk_size 不分块，整段入库

## 三、LangGraph Agent 与架构

### Q13：Agent 的整体架构（StateGraph 图结构）？

**考察点**：Agent 架构设计

**回答要点**：
- 状态：`AgentState(MessagesState)` 扩展 `retrieval_context` / `web_context` 两个字段（MessagesState 自带 messages 及 append reducer）
- 节点：`reset`（每轮清空上下文）→ `router`（入口路由）→ `retrieve`（前置检索）→ `web`（联网兜底）→ `agent`（LLM 调用）↔ `tools`（ToolNode 批量执行）
- 边与条件边：
  - START → reset；reset →（条件 skip/retrieve）
  - retrieve →（条件：无有效结果→web / 有→agent）
  - web → agent；agent →（条件：有 tool_calls→tools / 无→END）；tools → agent（ReAct 循环）
- 关键设计：检索上下文由 retrieve 节点注入 state，agent 节点拼进 SystemMessage（不污染消息历史）

### Q14：为什么要自定义 StateGraph，而不是用预置的 create_react_agent？

**考察点**：技术选型判断 + 框架理解深度

**回答要点**：
- **痛点**：预置 Agent 的执行顺序由 LLM 自主决定，“必须先检索”只能写在 Prompt 里——**软约束会漂移**（模型偶发跳过检索直接回答）
- **方案**：自定义 StateGraph 把 `retrieve` 做成**必经节点**——流程由图的边强制执行，不是模型自觉
- **附带收益**：Prompt 大幅精简（约束从文字移交给图结构）；埋点/降级（质量阈值、联网兜底）有了固定挂载点
- **数据**：知识类问题检索覆盖率 100%；动作类请求 10.8s → 1.5s、统计类 12.2s → 3.2s（跳过无谓检索）
- **边界感**：不是“自定义一定好”——create_react_agent 适合快速起步，需要硬控制流时才值得自定义

### Q15：入口路由怎么分类？为什么要“三分类”？

**考察点**：路由决策设计

**回答要点**：
- **设计**：问题分三类走向——① 社交/记忆/数学类：直接答（寒暄、指代回忆、算术不需要知识库）；② 动作指令类（删除/上传/发送/统计等）：跳过检索直接执行（`_ACTION_WORDS` + 正则模式）；③ 知识类：**默认强制前置检索**
- **实现**：关键词表 + 数学正则（`router` 函数条件边）
- **收益**：动作类 10.8s → 1.5s、数学类 11.2s → 2.5s；避免“查了也用不上”的无效检索
- **注意区分**：这是**图入口路由**（决定是否前置检索）；RAG 内部的**查询意图路由器**是另一个（决定检索通道 semantic/keyword）——两个路由各管一段，面试时别混淆

### Q16：工具集是怎么设计的？

**考察点**：Agent 工具设计

**回答要点**：
- **7 个 LLM 工具**（`@tool`）：`search_knowledge_base`（三阶检索全流程）、`upload_document`（异步入库）、`delete_document`（三联动清理）、`get_document_status`（统计+过滤）、`generate_report`（检索→汇总→Markdown）、`convert_format`（md/txt/docx 互转）、`send_email`（interrupt 审批 + SMTP + 附件）
- **web_search 特殊**：同一纯函数（`search_web`）既被 `web` 图节点复用（兜底链路），也包了一层 `@tool` 供模型主动调用——“一鱼两吃”避免逻辑重复
- **设计原则**：职责单一；docstring 写明“适用/不适用场景”供 LLM 路由；多参数工具必须配 `args_schema`（Pydantic）；返回值格式统一（字符串 + 结构化标记如 `[REPORT_FILE]`）

### Q17：真 token 级流式输出是怎么实现的？

**考察点**：流式架构

**回答要点**：
- **引擎**：`chain.astream_events(..., version="v2")`——消费三类事件：
  - `on_tool_start`：推送 `[调用工具: xxx]` 提示（Agent 轮的 tool_calls 触发）
  - `on_chat_model_stream`：token 级文本流——中间推理轮 function calling 的 content 为空自动跳过，只有最终回答流出（打字机效果）
  - `on_tool_end`：检测 `[REPORT_FILE]` 标记 → 文件名白名单校验（防路径注入）→ 推送 HTML 下载链接
- **SSE 编码**：`_sse_encode` 用 `json.dumps` 无损编码——修复早期 `\n` 转义方案把代码块换行与字面 `\n` 混淆的缺陷（帧数从个位数 → 数百）
- **持久化**：`finally` 块双写 HumanMessage/AIMessage 到历史 + 条件写缓存

### Q18：多轮对话记忆是怎么实现的（Checkpointer）？

**考察点**：LangGraph 持久化机制

**回答要点**：
- `AsyncSqliteSaver` 接入（lifespan 初始化），`thread_id = f"{user_id}_{session_id}"` 实现“用户+会话”双维度隔离
- **双写过渡**：checkpointer 接管**记忆注入**（图执行时自动带历史、增量模式防重复），JSON 文件继续作为**前端历史展示**的数据源——职责拆分而非简单替换
- **重启不丢**：状态落 SQLite（`checkpoints.db`）
- **联动清理**：会话删除时 `adelete_thread` 同步清记忆；修复过“缓存未按会话隔离导致跨会话复用”的缺陷

### Q19：记忆窗口（trim_messages）是怎么做的？为什么需要？

**考察点**：上下文工程

**回答要点**：
- **问题**：多轮+工具密集对话后消息列表膨胀，全量注入导致 token 成本与延迟上升，甚至有上下文溢出风险
- **方案**：`trim_messages` 滑动窗口——`max_tokens=20 + token_counter=len` 实现“最多保留 20 条消息”语义；`strategy="last"` 保留最新；`start_on="human"` **保证窗口从用户消息起头**（不把工具调用对裁成半截）；`include_system=False`（System 每轮现拼，不参与裁剪）
- **效果**：工具密集对话裁剪零异常
- **取舍**：早前轮次出窗后模型失忆——对短会话无感，超长会话下一步做摘要压缩（会话总结工具已列入排期）

### Q20：人工审批（HITL）是怎么实现的？

**考察点**：人机协同机制设计

**回答要点**：
- **中断**：`send_email` 工具内调用 `interrupt(payload)`（含收件人/主题/正文的结构化数据）→ 图挂起，状态定格在 checkpointer
- **传输**：流结束后后端 `aget_state` 收集 interrupts → 组装 `{type:"interrupt", payload, interrupt_id}` SSE 帧推给前端 → 渲染审批卡片（确认/取消）
- **恢复**：`POST /resume` → `Command(resume=decision)` 重新驱动图继续执行；`/pending` 查询会话是否有待审批
- **防呆**：待审批期间新消息在入口被拦截（检测 `task.interrupts`）+ 前端输入区锁定
- **健壮性**：审批状态在 checkpointer——切会话、刷新页面、重启服务全场景可恢复卡片；中断点前的操作幂等（interrupt 前不产生真实副作用）

### Q21：Agent 的 Prompt 是怎么设计的？

**考察点**：Prompt Engineering

**回答要点**：
- **结构**：人设（“你是 DevSage，面向研发团队……像同事对话一样自然”）+ 核心原则（有检索上下文直接用；不得凭训练知识回答）+ 例外清单（纯社交/数学/用户明确不查）+ 数据规则（检索结果是真实数据，禁止转述为“示例/假想”）+ 回答格式（来源标注、表格规范）+ few-shot 正例
- **temperature=0.3**：知识场景低温度，压制采样漂移
- **关键认知**：检索硬约束已由图结构承担，Prompt 相应精简——**约束放在正确的层**（结构管流程、Prompt 管风格）

### Q22：LangChain 工具定义有哪些坑？

**考察点**：框架实战经验

**回答要点**：
- `@tool` 使函数变 `StructuredTool`——不能直接调用，经 Agent 或 `.invoke()` 间接调用，结果取 `.content`
- **多参数工具必须配 `args_schema`**（Pydantic 模型），否则 LLM 脑补参数格式导致解析失败
- docstring 优先级高于函数名（工具描述以 docstring 为准）
- **参数脑补陷阱**：LLM 可能把纯文本当 JSON 传——`json.loads(strict=False)` 失败后走 `\n` 切分 fallback
- **命名约定**：用 `filename`/`content` 而非 `file_name` 类下划线命名，LLM 理解更稳定（实测）

## 四、文件解析与文档处理

### Q23：文件解析是怎么实现的？支持哪些格式？

**考察点**：文档处理能力

**回答要点**：
- 统一入口 `_extract_text(content: bytes, suffix: str) -> str`，按后缀分发：
  - `.txt` / `.md`：`content.decode("utf-8", errors="ignore")`
  - `.pdf`：`PyPDF2.PdfReader(BytesIO(content))` 逐页 `extract_text()`
  - `.docx`：`python-docx.Document(BytesIO(content))` 逐段 `para.text`
- `BytesIO` 内存流处理不落盘；每个格式有 `ImportError` 保护，缺依赖时抛明确异常
- 上传校验：大小 ≤10MB（`MAX_FILE_SIZE`）+ 后缀白名单；空内容检测拒绝入库

### Q24：MD5 去重是怎么实现的？删除为什么是“三联动”？

**考察点**：数据一致性设计

**回答要点**：
- **去重**：`get_string_md5(data)` 计算内容 MD5（按内容而非文件名，改名也能识别）→ 比对 `md5_records.txt` → 已存在拒绝入库；新文档分块入库后追加记录
- **删除三联动**（`delete_document`）：Chroma 切片段删除 + MD5 记录清理 + BM25 索引重建——三处状态一致，删除后同内容文件可重新上传（冒烟 8/8 通过）
- **为什么强调联动**：只删向量不删记录 → 无法重传；只删记录不删索引 → 检索幽灵片段。状态多副本就必须同步清理

### Q25：文档入库的元数据包含哪些信息？

**考察点**：向量数据库元数据设计

**回答要点**：
- 每个 chunk：`source`（来源文件）/ `create_time` / `operator`（上传者，多用户追溯）/ `md5` / `chunk_index` / `total_chunks` / `rerank_score`（Rerank 阶段写入，供质量阈值过滤）
- `source` 驱动**来源引用**：检索片段注入【来源：文件名】头 → Prompt 要求句末标注 + 尾部列引用来源（可解释 AI，来源由检索层保证而非模型编造）
- `chunk_index/total_chunks` 支持定位片段在原文中的位置

## 五、消息队列与异步处理

### Q26：为什么需要 RabbitMQ？异步上传流程是怎样的？

**考察点**：消息队列设计

**回答要点**：
- **同步问题**：PDF 解析 + 分块 + 向量化 + Chroma 写入 + BM25 重建耗时 10~30s，接口同步等待体验差
- **异步方案**：
  1. API 校验 → 文件内容 hex 写 Redis（`file:content:{task_id}`，600s 过期）
  2. 发消息到 Topic 交换机 `document.tasks`（routing_key=`document.upload`）→ 立即返回 HTTP 202 + task_id
  3. 内嵌 Worker（lifespan `asyncio.create_task`）消费 → hex 还原 → 解析 → 入库 → BM25 防抖重建
  4. 前端轮询 `GET /api/document/upload/status/{task_id}` 拿状态
- **为什么走 Redis 中转**：RabbitMQ 消息体不宜放文件内容（大小/持久化压力），内容暂存 Redis、消息只传指针

### Q27：RabbitMQ 消息的可靠性和幂等性怎么保证？

**考察点**：消息队列高级特性

**回答要点**：
- **可靠性四件套**：消息持久化（PERSISTENT）+ 死信队列（`x-dead-letter-exchange`）+ 手动 Ack（`async with msg.process()`）+ 消费重试（最多 3 次、间隔 5s）
- **幂等性**：Redis key `task:processed:{task_id}`（24h 过期），消费前检查——配合 at-least-once 语义防止重复入库
- 队列声明 `durable=True` + volume 挂载，Docker 重启队列不丢

### Q28：RabbitMQ 挂掉时系统怎么处理？

**考察点**：容错设计

**回答要点**：
- lifespan 中连接 try/except 包裹，失败 `logger.warning` + `mq_connected=False`——**不阻塞服务启动**
- 降级范围：异步上传功能禁用；检索问答、报告生成、邮件、认证完全正常
- **运维约束**：首次连接失败后不会自动恢复——需先启动 RabbitMQ/Redis 再启动后端（已写入 README 启动顺序说明）；这是“简单可靠优先”的取舍

### Q29：任务状态追踪怎么实现的？

**考察点**：异步任务状态管理

**回答要点**：
- `TaskTracker` 基于 Redis：key `task:document:{task_id}`，1h 过期，JSON 存状态
- 状态机：`Pending → Processing → Completed / Failed`
- 前端每 2s 轮询，终态停止
- 与幂等标记（`task:processed:`）分工：一个管“进度可见”，一个管“不重复执行”

## 六、缓存策略与一致性

### Q30：双层缓存是怎么设计的？

**考察点**：缓存架构

**回答要点**：
- **第一层：语义相似度缓存**（`SemanticCache`，内存向量）——历史问题向量存内存列表（LRU 上限 200 条），新问题编码后余弦相似度匹配，阈值 0.85；能命中“换一种问法”的相似问题
- **第二层：MD5 精确匹配**（Redis）——`hashlib.md5(question)`，key 按用户隔离，TTL 600s；完全相同提问直接返回
- **查询顺序**：语义 → MD5 → 正常流程；命中延迟约 20s → 约 0.01s
- **写入时机**：流结束 `finally` 条件写入 + 对话历史

### Q31：缓存一致性是怎么治理的？（重点）

**考察点**：缓存缺陷的自查与修复（高频追问）

**回答要点**（三个真实缺陷 + 修复）：
1. **“假成功”**：工具调用轮的回答被写入缓存——用户重复“删除某文档/发送邮件”指令时命中缓存，返回“已完成”但实际没执行 → 修复：**写侧**工具调用轮不写缓存（`not tool_times`）+ **读侧**动作指令（13 词表）拦截跳过缓存查找
2. **记忆类问句陈旧答案**：记忆指代类问题答案依赖对话历史，命中缓存会返回过期内容 → 三层防御：读侧拦截 + 写侧不写 + 图入口跳过前置检索
3. **跨会话复用**：缓存未按会话隔离，A 会话答案泄漏给 B → key 加用户维度 + 修复隔离逻辑
- **验证方式**：冒烟 6/6（同文删除两次均真实执行、删除后统计返回新状态、纯问答二次命中缓存正常）
- **纵深方向**：`SemanticCache.invalidate(user_id)` 主动失效（上传/删除后清语义缓存），比黑名单更彻底

### Q32：语义缓存的相似度怎么计算的？

**考察点**：向量计算原理

**回答要点**：
- DashScope Embedding 编码 → L2 归一化（`arr / np.linalg.norm(arr)`）→ 余弦相似度退化为点积（`np.dot`）
- `np.argmax` 取最相似项，阈值 0.85（平衡命中率与准确性）
- LRU 上限 200 条防内存膨胀；按用户隔离 key

### Q33：Redis 不可用时会影响哪些功能？

**考察点**：降级策略

**回答要点**：
- 懒加载 + 连接失败置 `_redis_client=None`；所有调用处判空降级
- **受影响**：双层缓存、异步上传（内容暂存）、任务状态追踪、幂等检查
- **不受影响**：检索问答、报告生成、对话历史（本地 JSON）、会话记忆（SQLite checkpointer）、JWT 认证（SQLite）
- **设计原则**：缓存/队列是增强件，核心问答链路不依赖它们

## 七、认证与安全

### Q34：JWT 认证是怎么实现的？

**考察点**：认证机制

**回答要点**：

### Q35：接口限流怎么做的？踩过什么坑？

**考察点**：安全防护 + 实战细节

**回答要点**：

## 八、前端全栈实现（Vue 3）

### Q36：前端是怎么实现的？为什么迁移到 Vue 3？

**考察点**：全栈能力 + 工程决策

**回答要点**：
- **技术栈**：Vue 3 + Vite；构建产物（`frontend/dist`）由 FastAPI 直接托管（无需额外进程）；Vite dev 模式代理 /api、/reports 到后端热更新联调
- **结构**：views（LoginView / ChatView）+ components（Sidebar / ChatArea / ApprovalCard）+ composables（useAuth / useSessions / useMessages，状态与 SSE 消费）+ utils/format.js（Markdown 渲染 + 表格规范化）
- **为什么迁移**：原生 HTML/JS 前端面条式代码、状态与 DOM 手动同步 → 组件化拆分 + composables 统一状态 + 响应式数据驱动（流式消息与审批状态机单一数据源）；同时提升工程观感（项目参赛需要）
- **保底**：Vue 未构建时自动回退旧 HTML 前端

### Q37：SSE 流式对话在前端怎么处理？

**考察点**：SSE 客户端实现

**回答要点**：
- 不用 `EventSource`（不支持 POST + 自定义 headers）→ `fetch + ReadableStream` 分块读取（`getReader` + `TextDecoder`）
- 逐行解析 `data:` 帧：普通文本 → JSON.parse 还原（无损）→ 增量渲染（打字机）；`[DONE]` 结束；`{type:"interrupt"}` 帧 → 渲染审批卡片
- 审批状态机是单一数据源：卡片显示/输入锁定/恢复都由它驱动；刷新/切会话后调 `/pending` 重建卡片
- buffer 拼接处理跨 chunk 截断的帧

### Q38：Markdown 渲染有什么注意点？

**考察点**：前端渲染细节

**回答要点**：
- `marked` 渲染标准语法（表格/代码块/标题/列表）良好
- **表格坑**：相邻表格/说明文字可能被吞并 → `normalizeTables` 规范化（相邻表格自动补空行）
- **特殊内容直推 HTML**：报告下载链接由后端直接推 `<a download>` 标签、工具调用提示独立渲染——绕过 marked 解析，防止被吞或转义错误

### Q39：数据库是怎么设计的？

**考察点**：数据库选型与设计

**回答要点**：

**考察点**：Python 跨层传参

**回答要点**：

- API 层 `current_user_ctx.set(user_id)` → Tool 内部 `current_user_ctx.get()`
- `contextvars` 协程安全：每个异步任务独立上下文副本（并发下不串用户）

### Q46：如果要把系统部署到客户内网，你会考虑什么？

- **环境差异**：Linux 系统依赖（如 libgomp1）、端口冲突、时区；健康检查与启动顺序文档化
- **交付物**：部署文档 + 一键脚本 + 回滚方案；现场问题排查（日志先行）
- 结尾落点：我项目里 Docker 一键部署全流程跑通过（三阶段构建/四服务编排/卷持久化），这套经验可以直接迁移

## 十一、系统设计对比

### Q47：为什么选 Chroma 而不是 Milvus / Qdrant / FAISS？

**考察点**：技术选型判断力

**回答要点**：
- 当前场景：小规模语料、单机部署、快速迭代 → Chroma 轻量零配置、嵌入式运行、Python 原生、与 LangChain 集成好、本地持久化
- Milvus/Qdrant 面向大规模分布式/高并发，当前数据量用不上，反而引入运维复杂度
- FAISS 纯内存索引性能高但无持久化（需自行序列化），适合临时计算（语义缓存就是内存向量点积的轻量模式）
- 升级路径：架构上向量层已解耦，docker compose 随时可加独立向量服务

### Q48：为什么用 FastAPI 而不是 Flask / Django？

**考察点**：框架选型

**回答要点**：
- 异步原生（`async/await` 一等公民）：Agent 流式调用 + SSE 推送 + RabbitMQ 异步消费 + LangGraph astream 天然契合
- Pydantic 类型校验 + 自动 OpenAPI 文档；`Depends` 依赖注入（认证、DB 会话）
- 不用 Django：只有一张用户表，全栈“电池全含”过重；不用 Flask：异步支持后来补的 + 无自动文档

### Q49：LLM 选型上为什么用 DeepSeek（硅基流动）？

**考察点**：API 选型

**回答要点**：
- OpenAI 兼容协议 → LangChain `ChatOpenAI` 零成本接入（改 base_url/api_key 即可）；“换模型”成本极低
- DeepSeek 性价比 + 中文能力适合中文知识库场景；Embedding 用 DashScope 中文向量
- temperature=0.3 适配知识问答场景

## 十二、Python / FastAPI 基础

### Q50：`@lru_cache` 在项目中怎么用的？

**考察点**：Python 装饰器

**回答要点**：
- `get_agent()` / `get_settings()` 单例：`@lru_cache(maxsize=None)` 全局唯一，避免重复构建图/重读配置
- 注意：装饰器必须带括号 `@lru_cache()`（否则 TypeError）；checkpointer 由 lifespan 先注入（`set_checkpointer`）再首次编译图，避免缓存到未注入的图
- 进程内缓存：改了实现要重启进程生效

### Q51：FastAPI 依赖注入（Depends）怎么用的？

**考察点**：FastAPI 核心特性

**回答要点**：
- `Depends(get_current_user)`：从 Bearer Token 解析 user，认证失败自动 401
- `Depends(get_db)`：DB 会话生命周期（yield → finally close）
- 收益：认证、限流、会话管理从业务代码里解耦

### Q52：Pydantic 和 pydantic-settings 的区别？

**考察点**：库分工理解

**回答要点**：
- pydantic：请求/响应模型校验（ChatRequest / UnifiedResponse 等 schemas）
- pydantic-settings：配置管理（.env → 类型安全 Settings）
- 统一收益：类型即文档（OpenAPI 自动生成）

## 十三、评测体系

### Q53：检索层评测是怎么做的？

**考察点**：数据驱动优化的意识

**回答要点**：
- 评测集 `eval_questions.json`：300 条（semantic/keyword 各 150，type 标注）
- 指标：Recall@K（Top-K 含预期关键词）+ MRR（首个正确结果排名倒数均值）
- `eval_retrieval.py` 多策略对比：Baseline / HyDEOnly / HyDE+Rerank / HyDE+BM25+Rerank / RouterStrategy（自适应）
- `eval_router.py` 路由校准：输出逐条 max_IDF 分布，验证三层漏斗阈值（4.0）
- 结论沉淀 EVALUATION.md：自适应 59.67% vs 全量混合 57.67%；30 题小集上 HyDE+Rerank 66.67%

### Q54：Agent 端到端评测怎么做？

**考察点**：评测工程（工程成熟度的信号）

**回答要点**：
- 38 题五分类：知识库 / 工具动作 / 联网 / 记忆 / 社交（含多轮指代、长窗口、防呆等压力题）
- **全自动断言、零 LLM judge**：工具命中（对照流内提示）/ 引用正则 / 联网双证据（标记 + 真实链接）/ 关键词子串
- 分组成功率 + 分类别延迟报告；**断点续跑**（改哪测哪）；配套 `scripts/maintenance.py` + `rerun.ps1` 一键重测
- 基线 38/38；实战案例：API 余额中断（402）导致 15 题环境性失败 → 凭断点续跑只重测失败题恢复全绿
- **失败归因三分类**：产品缺陷 / 评测题超纲 / 评测器误判——排查时的第一步分类

### Q55：压力题是怎么设计的？

**考察点**：测试设计能力

**回答要点**：
- 来源：真实调试中遇到的边界场景（工具参数脑补、缓存假成功、删除不存在的文件等）沉淀为固定用例
- 典型题“删除不存在的文件”：验证模型必须**真实调用 delete_document 工具**并如实返回“未找到”，而非凭常识编造成功
- **双重断言**：① 执行流中出现工具调用记录 ② 回答文本包含“未找到/不存在”关键词——缺一不可
- 意义：把调试经验固化为自动化回归，防止重构（如 StateGraph 改造）破坏错误处理链路

### Q57：项目中遇到最棘手的技术问题是什么？怎么解决的？
